# Decisions

Entries 1 to 20 come from the build prompt (§3) and resolve gaps in SRS v2.0. Entries from 21 on were made during the build, where the SRS and the prompt left something open. Each one picks the simplest option consistent with both.

## From the build prompt

1. **Missing collections.** Without the architecture document, collections such as `schools`, `classes`, `lessons`, and `enrollments` were undefined. The prompt's §6 defines them, and `apps/api/src/db.ts` mirrors it.
2. *Superseded (see 57: School Admins add teachers only; Content Admins create schools and School Admins).* **Account creation (FR-3.1.1).** Students sign themselves up. A School Admin creates teacher and student accounts for their school; right after the API creates the account, the web app calls Firebase's `sendPasswordResetEmail` so the new user can set a password. Content Admins (platform-level, not tied to a school) and the first School Admin are created by the seed script or `npm run create-admin`.
3. **Attempt history (FR-3.9.1).** `progress/{uid}_{activityId}` is the per-activity summary (latest score, best score, attempt count). Every attempt is stored in `attempts/{attemptId}`.
4. **Passing score.** Each quiz and test has `passingScorePct`, default 60.
5. **Streak (FR-3.9.2).** The number of consecutive calendar days with at least one graded attempt, counted in the user's time zone (default `Asia/Manila`).
6. **Server-side grading.** Question data sent to students never includes `correctIndex`. The server grades on submit and returns the score plus a review with the correct answers.
7. **Answer audio.** Audio on a quiz's correct answer (FR-3.5.2) appears only on the results and review screen. Flashcard audio shows normally.
8. **Two study areas (FR-3.6.1, FR-3.6.2).** Inside a class, a student sees only that class's teacher content, with no audio controls and no built-in items. Self-Study (built-in content for the student's chosen level) is a separate area every student can use.
9. **Lessons.** Flashcards and quizzes carry `lessonId`, so each class has simple lessons (title, order). Teachers pick the lesson when creating or importing content.
10. **Excel templates.** The SRS templates have no Level or Title column. The Content Admin picks the JLPT level in the upload form and it applies to every row. One quiz file creates one quiz; its title is typed in the upload form.
11. **Four choices everywhere.** Teacher quizzes require four choices (FR-3.4.1). Built-in quizzes, reading tests, and listening tests use the same four-choice (A to D) format, so one question editor serves all of them.
12. **No audio or video files in teacher materials**, consistent with the SRS rule that teacher content carries no audio (SRS 2.4, 2.5). Teachers can share videos as links.
13. *Superseded (see 56: classes are free).* **Payment happens at class enrollment.** The built-in self-study library stays free. The payments module has a `purpose` field so a paid library pass could be added later.
14. **One merchant account.** Online payments go to the single PayMongo account configured in env. Each School Admin sees and manages only their school's payments.
15. *Superseded (see 56).* **School Admins set fees.** A class created by a Teacher is free until the School Admin sets a fee. Fee changes apply to new enrollments only.
16. **Role source of truth (SRS 5.2).** On every request the API verifies the Firebase ID token, then reads the role from `users/{uid}`. Custom claims are never used by the API.
17. **No direct Firestore or Storage access from the browser.** The frontend talks only to the API over HTTPS/JSON. Firestore and Storage rules deny all client reads and writes; the API uses the Admin SDK.
18. **In-app notifications only.** No email or SMS service: Google Calendar sends class invites, PayMongo sends payment receipts, and Firebase sends account emails.
19. **Archived classes** stay readable for their students but accept no new joins, sessions, content, or materials.
20. **Mock payments for development.** `PAYMONGO_MODE=mock` runs the whole payment flow, including the real webhook code, without a PayMongo account.

## Made during the build

21. **Removing a person deactivates them.** `DELETE /users/:uid` disables the Firebase account, sets `disabled: true`, and marks the person's active and pending enrollments `removed`. Attempts, attendance, and payments stay, so reports and receipts remain correct. A teacher must be unassigned from every class first.
22. *Superseded (see 57).* **Adding an existing student.** When a School Admin adds a student whose email already belongs to a self-registered student with no school, the account is linked to the school instead of failing. Any other existing account returns 409 `email_in_use`.
23. **Role changes.** A School Admin can switch an account between teacher and student (audit-logged). A teacher who is still assigned to a class can't be switched. School Admin and Content Admin roles are only set by the CLI.
24. **Streak end day.** A streak ends today, or yesterday if nothing has been graded yet today, so it isn't shown as broken until a whole day passes without study.
25. **Extra routes.** `GET` and `PATCH /schools/:schoolId` (school settings, including manual-payment instructions) and `GET /notifications/unread-count` (the badge in the navigation) were added to the §11 outline.
26. **Google is optional locally.** The Google OAuth variables may be empty. Without them, Settings explains that Google isn't configured and scheduling always uses a pasted Meet link (FR-3.11.4). All other variables in §15 are required.
27. **Tests clear the emulators.** The API suite deletes all emulator data before it runs. After running tests against the dev emulators, run `npm run seed` again.
28. **Privacy consent is enforced by the web app.** The API records `privacyConsentAt` at registration and through `PATCH /me`; the web app blocks every screen until consent is recorded.
29. *Superseded (see 56; refunds no longer apply to classes).* **Rejoining after removal.** A student a teacher removed can't rejoin with the class code; the teacher adds them back from the roster. A refunded student can pay again.
30. **Students and schools.** A self-registered student has no school until they first join a class or are added to one; they are then linked to that class's school so its admins see them in People. Enrollments always carry the class's `schoolId`.
31. *Superseded (see 56: there is no locked class view).* **Locked class view.** A `pending_payment` student can open `GET /classes/:id` (name, fee, payment options, including the school's payment instructions) to see the locked page. Lessons, study, live classes, materials, and file tickets all return 403 `payment_required`.
32. **Roster adds need an account.** Staff add students by the email of an existing student account. A School Admin can create the account first in People.
33. *Superseded (see 56).* **Offline payments and waivers.** Recording an offline payment creates a `payments` document (provider `offline`, status `paid`) so it appears in totals, exports, and receipts. A waiver creates no payment; it sets `paymentStatus: waived` and is audit-logged. Marking a student unpaid is audit-logged too.
34. *Superseded (see 56).* **Refunds.** Marking a payment refunded sets the enrollment to `refunded` with `paymentStatus: unpaid`. A late paid event for a refunded payment changes nothing. Receipts stay viewable and say the payment was later refunded.
35. **Attendance rate.** (present + late) / (present + late + absent). Excused absences don't count. Staff can edit attendance from 15 minutes before the start.
36. **Built-in audio URLs.** In production the API calls `getDownloadURL()`. Against the Storage emulator that call is refused by the deny-all rules, so the API builds the identical download-token URL from the token it just set.
37. **Recorded audio MIME type.** Multer keeps only the base MIME type, so the browser sends the recording's full type (for example `audio/webm;codecs=opus`) as a `mimeType` form field, which is stored when it matches the detected container.
38. **Audio is attached only by upload.** Built-in quiz questions accept an `audioUrl` on update only when it already belongs to that quiz (so reordering keeps audio). A client can't point audio at another address.
39. **Routes added to the §11 outline.** `GET /quizzes/:id` (teacher quiz editor), `GET /library/:type/:id`, `GET /library/overview`, `DELETE /library/:type/:id/audio`, `POST /library/:type/batch/:batchId/publish` (review screen), `GET /materials/:id`, and `GET /dev/mock-paymongo/:paymentId` (mock checkout page data).
40. **Import review matching runs in the browser.** Imported rows keep the Excel `Audio File Name` as `expectedAudioName`. The review screen matches dropped files by name (case-insensitive), lists unmatched files and rows, and uploads each match through `POST /library/:type/:id/audio`.
41. **Listening tests need their clip to publish.** A listening test is created as a draft and can be published once its clip is uploaded; the clip can't be removed while it's published.
42. **Weekly series are all or nothing with Google.** Google's Calendar docs warn against reusing Meet conference data across events, so each session gets its own event. If an insert fails partway through a series, the events already created are deleted and the API asks for a pasted link (409 `meet_link_required` with a `reason`). A `useGoogle` field lets a host with Google connected paste a link anyway.
43. **Session rules.** A session must end in the future when scheduled. Only scheduled sessions can be edited; completed ones can't be cancelled. The first check-in is kept, and a status a teacher set is never overwritten by a later Join click.
44. **School Admins host live classes too.** They can connect Google in their Settings and schedule, edit, and cancel sessions for any class in their school.
45. **PayMongo endpoint and payload.** The Hosted Checkout quick start uses `https://api.paymongo.com/v2/checkout_sessions` (the API reference page shows a `/v1` path with "version 2"); the app uses v2 as the prompt and quick start do. PayMongo's docs don't show a `checkout_session.payment.paid` example, so the handler reads the session at `data.attributes.data` and treats it as paid when a payment in `attributes.payments` has `status: "paid"` (amount from that payment), falling back to `payment_intent.attributes.status == "succeeded"`. Retrieval (`GET /v2/checkout_sessions/{id}`) is read the same way. Confirm with PayMongo's "send test event" before going live; development logs every webhook payload.
46. **Webhook details.** The signature is compared with `li` when `PAYMONGO_MODE=live` and with `te` otherwise. The optional timestamp tolerance isn't enforced, since de-duplication already blocks replays. If processing fails, the `paymentEvents` record is deleted and 500 is returned so PayMongo's retry is processed.
47. **Mock mode calls the webhook handler in-process.** The mock Pay route builds and signs the event exactly as PayMongo does and passes it to the same function the webhook route uses (signature check included), rather than making an HTTP request to itself. This works identically in tests and development.
48. *Superseded (see 56; the proof option is gone).* **Checkout failures.** If PayMongo can't create a session, the pending payment is deleted and the API returns 503 `provider_unavailable`; the web app shows "Online payment isn't available right now" and the proof option when the school allows it. A pending checkout is reused within the hour only while the class fee is unchanged.
49. **Money received always counts.** A paid event (or reconciliation) for an expired, rejected, or needs-review payment still marks it paid and activates the enrollment, unless the amount doesn't match. Approving a `needs_review` payment in the verification queue also activates it.
50. **File delivery headers.** Ticketed file responses drop the API's CSP and `X-Frame-Options` and set `Cross-Origin-Resource-Policy: cross-origin` so the web app (another origin in production) can show them in an `<iframe>` or `<img>`. Only PDFs and images are served inline; everything else is forced to download. Uploads are magic-byte checked, so no HTML or SVG is ever served.
51. **Publishing a material** requires at least one file, link, or a description. Materials without a lesson are grouped under "General".
52. **Where files live.** Built-in audio: `builtin/audio/{type}/{id}/{uuid}.{ext}`. Class materials: `classes/{classId}/materials/{materialId}/{attachmentId}-{name}`. Payment proofs: `payments/{schoolId}/{paymentId}/proof-{random}.{ext}`, served only through tickets to the payer and that school's admins.
53. **Rate limits (per user, or per IP before sign-in, per 15 minutes).** Registration 20, class-code preview 30, join 20, checkout 20, proof uploads 10, file tickets 120, file downloads 300, Google connect 20, Google callback 30.
54. **Self-Study decks.** "Study in order" pages through the level's cards, 50 at a time, as the student nears the end; "Random deck" is 50 cards from a random `shuffleKey` start.
55. **Keeping zod out of the student bundle.** The web app validates class codes with the shared alphabet constant rather than the zod schema, so student screens don't download zod. Vendor code is split into long-lived `vendor-react` and `vendor-firebase` chunks.

## Billing change (October 2026)

The tuition model above was replaced. Classes are free; the app charges schools for extra teachers and teachers for Premium.

56. **Classes are free.** Class fees, payment-locked enrollments, proof-of-payment uploads, offline payments, waivers, and the School Admin payments area were removed. Enrollments are `active` or `removed`. The `payments` collection and the PayMongo flow (Hosted Checkout, signed webhook, de-duplication, reconciliation, expiry, mock mode) stay, with two purposes: `teacher_seats` and `premium`.
57. **Who creates accounts.** Students sign up in the app themselves (the role is always `student`). A School Admin adds teachers only (`POST /schools/:id/users` accepts no other role, and an email that already has a profile is refused). Only a Content Admin creates a school, together with its first School Admin (`POST /schools`), and adds or removes School Admins (`/schools/:id/admins`); a school always keeps at least one. Each new staff account gets Firebase's set-password email from the browser, as before.
58. **Teacher slots.** Every school has 5 free teacher slots. A pack of 5 more costs ₱299.00, paid once, and never expires (`schools.extraTeacherSeats`). Up to 20 packs per checkout. Each teacher who isn't disabled uses a slot, so removing a teacher frees one. Adding or re-enabling a teacher with no free slot returns 402 `seat_limit_reached`. Existing teachers are never disabled when a school is over its limit.
59. **Teacher Premium.** ₱299.00, paid once; Premium never expires (`users.premiumSince`). A teacher who has it can't start another Premium checkout (409 `already_premium`). If two checkouts started in different tabs are both paid, both payments are recorded and the first date is kept; refunding the extra one is done in the PayMongo dashboard. The webhook grants Premium; the browser never does.
60. **Needs review.** An amount mismatch sets `needs_review`, grants nothing, and notifies the payer. A paid event for an expired payment still counts, as before.
61. **In-app video calls.** WebRTC in the browser (a mesh of up to 8 people) with a WebSocket signaling endpoint on the API (`/api/calls/ws`, same port). The first message must be `join` with the call id and a Firebase ID token; the API checks class access exactly as the REST routes do. A teacher or School Admin of the class starts a call; enrolled students join from the class page or the notification. One active call per class.
62. **Call length.** A call ends at `startedAt + limit`: 5 minutes, or 15 when the host has Premium when starting. A host who buys Premium during a call can extend it to 15 minutes from its start. The server ends the call on time (a timer per call), and an active call past its end is closed whenever it's read, so a restart can't leave it running. A call nobody is in for 2 minutes ends by itself. Google Meet live classes are unchanged and have no time limit.
63. **Calls need one API instance.** Call rooms live in the API process's memory. Run a single API instance while calls are used (on Cloud Run, `max-instances=1` with session affinity), or move rooms to a shared store before scaling out. STUN uses Google's public server; set `TURN_URLS`, `TURN_USERNAME`, and `TURN_CREDENTIAL` for networks where peer-to-peer fails.
64. **My Drive.** Each teacher has private folders and files (`driveItems`, files at `drive/{uid}/...`), served only to the owner through the same signed tickets as materials. Allowed types match class materials (no audio or video, decision 12). Deleting a folder deletes everything in it.
65. **One storage quota.** My Drive files and class material files a teacher uploads share one quota: 500 MB free, 1 GB with Premium (`users.storageUsedBytes`). Space is reserved in a transaction before a file is stored and released when it's deleted or the upload fails; a material deleted by a School Admin gives the space back to the teacher who uploaded it. Uploads by School Admins aren't counted. When Premium ends nothing is deleted, but uploads stop until usage is under 500 MB.
66. **Routes added.** `GET /billing/school`, `POST /billing/teacher-seats/checkout`, `GET /billing/premium`, `POST /billing/premium/checkout`, `GET /schools`, `POST /schools`, `POST` and `DELETE /schools/:id/admins`, `/drive` (list, folders, files, rename and move, delete, ticket), `/classes/:id/calls` (start, active), `/calls/:id` (get, end, extend), and `GET /calls/ice`. `/me` includes the teacher's plan.
67. **Storage can be Supabase.** `STORAGE_PROVIDER=supabase` sends uploaded files to Supabase Storage (free plan, no card) while Auth and Firestore stay on Firebase. Two buckets are created on first use with the secret key: a private one for materials and My Drive, streamed only through the API's tickets (the API fetches a 60-second signed URL server-side, so Supabase URLs never reach the browser), and a public one for built-in audio, whose public URLs replace Firebase download-token URLs. Paths are unique across both, so a delete removes the path from both. The default stays `firebase`, which the emulators and the test suite use; a separate test runs the Supabase code against a fake Supabase API.
